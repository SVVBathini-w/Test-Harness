Run the gate: **$ARGUMENTS**

Follow `CLAUDE.md` section 8.

## Reviewer independence

`code_quality`, `traceability` and `session_score` run as **fresh** `qa-lead` invocations. Never continue a context that produced the artefacts under review. If you already hold the authoring context, say so and start a new agent — a review that watched itself write the code is void.

## Gate rules

| Gate | Agent | Passes when |
|---|---|---|
| `execution` | qa-executor | Suite actually ran and zero failures are unclassified |
| `code_quality` | qa-lead `MODE: review` | Zero critical or high findings open |
| `traceability` | qa-lead `MODE: trace` | Coverage 100, four directions closed, zero orphans |
| `reporting` | qa-lead `MODE: report` | All metrics present and internally consistent |
| `session_score` | qa-lead `MODE: score` | Score ≥ 28 — warns, does not block |

## Never decide a gate by string matching

Searching a report for "BLOCKING" or "Gap" fails, because those words appear in every correctly written report. The gate is decided by the schema-validated object, and nothing else.

## Procedure

1. Launch the owning agent in the right mode.
2. It emits `<projectDir>/runs/<run-id>/gate-<name>.json` (the latest run; `traceability` is generated by `node bin/qa-reports.mjs traceability <slug>`, not written by the agent) conforming to `schemas/gate-result.schema.json`.
3. Validate it — an invalid gate object is not a result:

```
node bin/qa-validate.mjs gate-result <projectDir>/runs/<run-id>/gate-<name>.json
```

4. Record it:

```
node bin/qa-state.mjs set-gate <slug> <name> <pass|fail|warn> [coverage=N] [blocking=N] [score=N]
```

## Report

State pass or fail, the deciding number, every blocking finding with its responsible artefact, and the specific remediation. For a failure, name what must change and who changes it — never just that it failed.

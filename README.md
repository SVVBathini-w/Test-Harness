# Testharness

An autonomous QA harness for [Claude Code](https://claude.com/claude-code). Five specialised agents run a 13-phase pipeline that turns a requirements document, a user story or a live application into risk-based test intents, automated tests, executed results, confirmed defects and a release assessment.

It is built around four ideas:

- **Evidence over assumption.** An agent states what it observed, with its provenance. A business rule that is not stated is `UNKNOWN`, never invented.
- **Machine data is produced by code.** Test results, traceability, defect mirrors and every report are generated by scripts from the data on disk. Agents record judgement; scripts record facts.
- **Everything governed is schema-validated.** Every artefact the pipeline reads has a JSON Schema, checked when it is written and again when it is read.
- **A person decides only what is not an agent's to decide.** The pipeline runs autonomously and stops only at a small set of *holds*: authorisation, environment safety, where code may be written, and a few others.

## How it works

```
                  you                                        harness (this repository)
   requirements, story, URL, repo                 agents · skills · schemas · scripts · hooks
              │                                                      │
              ▼                                                      ▼
      /qa-intake  ───────────►  ~/testharness-projects/<slug>/   ◄──── the only place agents write
      /qa-run                    ├── spec/      what must be proven
      /qa-triage                 ├── analysis/  what exists
      /qa-impact                 ├── registry/  inventory · defects · history
                                 ├── suite/     the automated tests
                                 ├── runs/      one folder per execution
                                 └── reports/   generated by script
```

The harness and the projects it tests are separate. **This repository holds no project data.** A project lives in its own folder, either created for it under `~/testharness-projects/<slug>/` (*new* mode) or in a `qa/` folder beside a test repository you already have (*existing* mode).

Work is divided between five agents. Each owns specific artefacts and modes, and no agent writes another's:

| Agent | Phases | Responsibility |
|---|---|---|
| `qa-architect` | 1–4 | Requirements, risk, strategy, test intents. Decides what must be proven and why, never how it is coded. |
| `qa-analyst` | 5–6 | Discovery, coverage, gap, change impact. Inspects what exists and decides reuse versus create. |
| `qa-engineer` | 7–8 | Layer designs, test cases, framework setup, automation code. |
| `qa-executor` | 9 | Runs the suite, explores, triages failures, confirms defects, bounded self-healing. |
| `qa-lead` | 0, 10–12 | Scaffolds projects, reviews independently, proves traceability, assesses release quality, scores, captures knowledge. |

## Requirements

- **Node.js 22 or later.** The harness has no dependencies of its own.
- **Claude Code.** The only supported agent tool.
- Per project: whatever the project's test suite needs. A new project's `suite/` is a Playwright project, so it needs `npm install` and `npx playwright install`.

## Quick start

```bash
# 1. Get the harness and check it
git clone <repository-url> testharness && cd testharness
npm test

# 2. Create a project (new mode)
node bin/qa-init.mjs --new my-app --name "My App" --url https://staging.example.com
#    ...or, beside a repository that already has tests (existing mode):
node bin/qa-init.mjs --repo my-app --path /path/to/that/repo

# 3. Install the new project's suite once (new mode only)
cd ~/testharness-projects/my-app/suite && npm install && npx playwright install && cd -

# 4. Start Claude Code from the harness with the project in scope
TESTHARNESS_PROJECT_DIR="$HOME/testharness-projects/my-app" claude
#    qa-init prints this command with the right paths. For an existing repo the
#    project directory is <repo>/qa.
```

Then, inside Claude Code:

```
/qa-intake path/to/requirements.md my-app     phases 0–2: requirements and risk
/qa-run my-app                                phases 3–12: strategy through learn
```

`/qa-run` starts with `bin/qa-plan.mjs`, which refuses to launch while a blocking gate has failed or a decision is pending. If an agent raises a *hold*, the run stops and says which one. You answer it **in your own terminal**:

```bash
node bin/qa-decisions.mjs list  my-app --status pending
node bin/qa-decisions.mjs grant my-app D-1 --rationale "Approved by the environment owner"
```

When a run finishes, read `~/testharness-projects/my-app/reports/report.html`.

Other entry points: `/qa-triage` classifies the failures of the latest run, `/qa-impact <ref>` selects and runs a defended regression set for a change, `/qa-gate <gate>` runs one quality gate alone, `/qa-learn` captures durable knowledge.

## Project structure

Every project, in either mode, has the same layout. In *new* mode it is `~/testharness-projects/<slug>/`. In *existing* mode it is `<repo>/qa/`, and the suite is the team's own test directory instead of `suite/`. The single source of these paths in code is `bin/lib/layout.mjs`.

```
<project>/
├── project.json          identity, mode, target, stage, gates, framework, suite, latest_run
├── .env.example          every variable the suite reads, with placeholder values
├── .gitignore            runs/, node_modules/, .env
├── inputs/               what people provided
├── spec/                 WHAT must be proven
│   ├── requirements.md
│   ├── risks.json
│   ├── strategy.md
│   ├── intents.json
│   ├── decisions.json
│   ├── design/layer-<n>.md
│   └── cases.md
├── analysis/             WHAT exists
│   ├── discovery.json
│   ├── coverage.json
│   ├── hotspots.json
│   └── changes/<change-id>.json
├── registry/             long-lived records
│   ├── inventory.json
│   ├── defects.json
│   ├── heals.json
│   ├── scores.json
│   └── evidence/<DEF-id>/
├── knowledge/            optional durable knowledge
├── suite/                the test project
├── runs/<run-id>/        one folder per execution
└── reports/              generated by script only
```

| Path | What it is | Written by |
|---|---|---|
| `project.json` | The project's identity and state machine. Schema `project`. Described [below](#the-projectjson-schema). | `qa-init`, then `qa-state`, `qa-runs` and the agents that own a field |
| `.env.example` | The environment variables the suite reads, placeholders only. The real `.env` is gitignored and never committed. | `qa-init`; `qa-engineer` (`setup`) extends it |
| `inputs/` | Material people supplied: requirement documents, defect CSVs, answers to open questions. Never edited by agents. | You, or `qa-lead` (`init`) copying the source in |
| `spec/requirements.md` | The requirement register: numbered requirements (`R-001`…), business rules, acceptance criteria, enrichment and open questions, each with its provenance. | `qa-architect` (`requirements`) |
| `spec/risks.json` | The risk register. A risk is a consequence, scored by likelihood and impact (1–5), with the layers that address it. Also holds the assumption log and the out-of-scope list. Schema `risks`. | `qa-architect` (`risk`) |
| `spec/strategy.md` | Risk-driven allocation of effort: which layers, what each proves, oracles, test-data strategy, entry and exit criteria, deliberate exclusions. | `qa-architect` (`strategy`) |
| `spec/intents.json` | The Test Intents: one per unique behaviour, each with a layer, an oracle and evidence. The unit of QA work. Schema `test-intent`. | `qa-architect` (`intents`) |
| `spec/decisions.json` | Human holds and records: who decided what, when and why. Schema `decisions`. Agents may raise a hold but cannot answer one. | `qa-decisions` |
| `spec/design/layer-<n>.md` | The design for each enabled layer: components required, data required, one line per intent naming its oracle and approach. | `qa-engineer` (`design`) |
| `spec/cases.md` | The test cases, one row per case, tracing to exactly one intent. | `qa-engineer` (`cases`) |
| `analysis/discovery.json` | What exists: stack, existing assets, conventions, observed selectors, interaction patterns, history, testability findings. Schema `discovery`. | `qa-analyst` (`discovery`) |
| `analysis/coverage.json` | A baseline of existing tests and, per intent, the reuse-or-create decision. Schema `coverage`. | `qa-analyst` (`coverage`, `gap`) |
| `analysis/hotspots.json` | Where defects are likely to hide, with evidenced signals and an effort allocation. Schema `hotspot-model`. | `qa-analyst` (`discovery`, `impact`) |
| `analysis/changes/<id>.json` | One file per analysed change: files, selected and excluded tests, blast radius, residual risk. Schema `change-impact`. | `qa-analyst` (`impact`) |
| `registry/inventory.json` | Every test with its regression tier and class, oracle strength, reliability, debt and lifecycle. Schema `test-inventory`. Seeded in phase 7, filled in phase 9, governed in phases 10–12. | `qa-engineer`, `qa-executor`, `qa-lead` for their own fields |
| `registry/defects.json` | The authoritative defect register. Schema `defect-record`. | `qa-executor` via `qa-defects` |
| `registry/heals.json` | Append-only log of every self-healing change. Schema `heals`. | `qa-executor` (`heal`) |
| `registry/scores.json` | Append-only history of the 8-dimension session score. Schema `scores`. | `qa-lead` (`score`) |
| `registry/evidence/<DEF-id>/` | A confirmed defect's evidence, copied out of the run it came from so it survives pruning. | `qa-defects promote` |
| `knowledge/` | Optional durable knowledge with provenance: `patterns/`, `defects/`, `decisions/`, `INDEX.md`, `improvement-log.md`. Schema `knowledge-record`. | `qa-lead` (`learn`) |
| `suite/` | The automated tests: its own `package.json`, runner config and `tests/<layer>/`. In *existing* mode this is the team's own test directory, recorded in `project.json` → `suite.path`. | `qa-engineer`; `qa-executor` (`heal`) edits tests within the healing boundary |
| `runs/<run-id>/` | One folder per execution, never overwritten, gitignored. See below. | The runner, `qa-results`, and the agents named below |
| `reports/` | Generated reports. No agent can write here. | `qa-reports`, `qa-defects mirror`, `generate-html-report` |

### A run

`runs/<run-id>/` holds one execution. The id is `YYYYMMDD-HHMMSS-<hex>`, created by `qa-runs new`, and `project.json` → `latest_run` points at the newest. The runner writes into it through the `TH_RUN_DIR` environment variable, which has no default.

| File | Contents | Written by |
|---|---|---|
| `run.json` | Scope, budget, change reference, commit, start time. Schema `run`. | `qa-runs` |
| `results.json` / `results.xml` | The raw runner report. Large; agents never read it. | The runner |
| `summary.json` | Totals, per-layer counts, failures and untraced tests, parsed from the raw report. | `qa-results` |
| `evidence/` | Traces, screenshots, response captures. | The runner and `qa-executor` |
| `triage.json` | A classification and root cause for every failure. Schema `triage`. | `qa-executor` (`triage`) |
| `exploration.md` | Exploratory-testing charters and findings. | `qa-executor` (`explore`) |
| `review.json` | Independent review findings and evidence coverage. Schema `review`. | `qa-lead` (`review`) |
| `assessment.json` | The release verdict, residual risk, what was not tested. Schema `assessment`. | `qa-lead` (`report`) |
| `gate-<name>.json` | One file per quality gate. Schema `gate-result`. | The owning agent, or `qa-reports` for traceability |

### `reports/`

| File | Contents |
|---|---|
| `report.html` | The self-contained HTML report. |
| `report.md` | The QA report: recommendation, results, defects, evidence quality, gates, residual risk, next actions. |
| `execution.md` | Totals, per-layer table, failures with their classes, heals, untraced tests. |
| `traceability.md` | Requirement → intent → case → test closure, and the orphans. |
| `defects.md` | A readable mirror of `registry/defects.json`. |
| `review.md` | The independent review findings. |

## The `project.json` schema

`project.json` is both the project's identity and its state machine. It is validated against `schemas/project.schema.json` every time it is written.

| Field | Type | Meaning |
|---|---|---|
| `name` | slug | Kebab-case, 2–4 words, at most 40 characters. The project's identifier. |
| `display_name` | string | Human-readable name. |
| `mode` | `new` \| `existing` | Where the project lives and who owns the suite. |
| `layout_version` | `1` | The project directory layout; see `bin/lib/layout.mjs`. |
| `target` | object | What is under test: `kind`, `base_url`, `environment` (`local`, `dev`, `test`, `staging`, `demo`, `shared`, `production`, `unknown`) and `authorised`. A `production`, `shared` or `unknown` environment holds execution until a person grants it. `authorised` is a claim; layers 7 and 8 additionally need a granted `authorisation` decision. |
| `source_document` | string | Project-relative path of the requirement source. |
| `stage` | enum | The phase last reached: `intake`, `requirements`, `risk`, `strategy`, `intents`, `discovery`, `gap`, `design`, `build`, `execute`, `verify`, `report`, `learn`, `complete`. A claim about progress; artefacts on disk are the evidence, and `qa-state resume` trusts them over this field. |
| `layers` | array | Enabled test layers, 1–8. A disabled layer is excluded from every denominator, never counted as covered. |
| `framework` | object | The automation stack, *discovered* rather than assumed: language, runner, e2e/api/a11y/perf tools, package manager, and a mandatory `selection` block recording why. The template carries `_placeholder: true` until phase 5 decides. |
| `suite` | object | `path` of the test project. Mode *new*: relative to the project, normally `suite`. Mode *existing*: relative to the repository root, recorded by phase 5; until then nothing may be written there. |
| `gates` | object | The five quality gates, each `pending`, `pass` or `fail` (`session_score` may also `warn`), with the run that produced the verdict. |
| `latest_run` | run id \| null | The newest run. Set only by `qa-runs`. |
| `team` | object | Optional ownership information. |
| `counters` | object | Idempotency counters, so re-running a phase does not count an artefact twice. |
| `created`, `updated` | date | ISO-8601. |
| `notes` | string | Free text; a forced override must be explained here. |

The five quality gates:

| Gate | Phase | Passes when | Blocks |
|---|---|---|---|
| `execution` (G1) | 9 | Every failure is classified with a root cause | yes |
| `code_quality` (G2) | 10 | No critical or high finding is open | yes |
| `traceability` (G3) | 10 | Four-direction closure with zero orphans | yes |
| `reporting` (G4) | 11 | Every metric present and consistent with the facts | yes |
| `session_score` (G5) | 11 | Score of 28 or more out of 40 | warns only |

## Commands and tools

Slash commands, run inside Claude Code:

| Command | Does |
|---|---|
| `/qa-intake <source> [slug]` | Phases 0–2: scaffold, requirements, risk. |
| `/qa-run <slug> [--from N] [--scope S] [--budget lean] [--change <ref>]` | Phases 3–12 through the pipeline workflow. Plans first and obeys the plan. |
| `/qa-triage [slug] [test]` | Classify the latest run's failures, adversarially verify product-defect claims, register the upheld ones, heal what is safe. |
| `/qa-impact <ref> [slug]` | Trace a change to a regression set, challenge every exclusion, run the selection. |
| `/qa-gate <gate> [slug]` | Run one quality gate alone. |
| `/qa-learn [slug]` | Phase 12 alone: knowledge capture and inventory governance. |

Command-line tools, run from the harness directory:

| Tool | Does |
|---|---|
| `qa-init` | Scaffold a project (`--new <slug>` or `--repo [slug] [--path <repo>]`). |
| `qa-plan` | Pre-flight for `/qa-run`: state, gates, holds, scope, run; emits the workflow arguments. Exit 0 ready, 1 blocked. |
| `qa-state` | Read and change project state: `list`, `show`, `resume`, `set-stage`, `set-gate`, `gate-audit`. |
| `qa-runs` | One folder per execution: `new`, `latest`, `list`, `show`, `compare`. |
| `qa-results` | Parse a run's raw report into `summary.json`. |
| `qa-reports` | Render `reports/` from the data: `execution`, `traceability`, `review`, `report`, `all`. |
| `generate-html-report` | Render `reports/report.html`. |
| `qa-intents` | Read slices of the intent file: `summary`, `layer`, `tag`, `ids`, `get`. |
| `qa-defects` | The defect register: `new`, `add`, `list`, `search`, `show`, `ids`, `mirror`, `promote`, `push`. |
| `qa-decisions` | Human holds: `ask`, `list`, `pending`, `require`, `grant`, `deny`. |
| `qa-validate` | Validate a file against a schema, by name or inferred from its path. |
| `qa-cost` | Estimate the token volume of what agents generated. |

## The 13-phase pipeline

| # | Phase | Agent · mode | Produces |
|---|---|---|---|
| 0 | Intake | `qa-lead` · `init` | `project.json` |
| 1 | Requirements | `qa-architect` · `requirements` | `spec/requirements.md` |
| 2 | Risk | `qa-architect` · `risk` | `spec/risks.json` |
| 3 | Strategy | `qa-architect` · `strategy` | `spec/strategy.md` |
| 4 | Intents | `qa-architect` · `intents` | `spec/intents.json` |
| 5 | Discovery | `qa-analyst` · `discovery` | `analysis/discovery.json`, `analysis/hotspots.json` |
| 6 | Gap | `qa-analyst` · `coverage`, `gap` | `analysis/coverage.json` |
| 7 | Design | `qa-engineer` · `design`, `cases` | `spec/design/`, `spec/cases.md`, `registry/inventory.json` |
| 8 | Build | `qa-engineer` · `setup`, `automation` | the suite |
| 9 | Execute | `qa-executor` · `execute`, `explore`, `triage`, `heal` | `runs/<id>/` results and triage, `registry/defects.json` |
| 10 | Verify | `qa-lead` · `review`, `trace` | `runs/<id>/review.json`, traceability gate |
| 11 | Report | `qa-lead` · `report`, `score` | `runs/<id>/assessment.json`, `registry/scores.json`, `reports/` |
| 12 | Learn | `qa-lead` · `learn` | `knowledge/` |

[`docs/pipeline.md`](docs/pipeline.md) describes how each phase is implemented.

## Safety model

- **Write scope.** A `PreToolUse` hook confines agents to the project in scope: the whole project folder in *new* mode; `qa/` plus the recorded suite directory in *existing* mode. It always protects `reports/`, `spec/decisions.json`, the project's `.claude/` and `CLAUDE.md`, and every harness file. With no project in scope the hook does nothing, so the harness stays editable.
- **Holds.** Seven decision kinds stop the run until a person answers: `authorisation` (layers 7 and 8), `environment` (production, shared or unknown), `test_location` (existing repositories), `business_rule`, `framework_change`, `bulk_retirement` and `tracker_push`. The hook refuses an agent that tries to grant or deny one.
- **Generated reports.** Reports are rendered from data. The QA report refuses an assessment the facts contradict, such as a pass-grade verdict while a confirmed high-severity defect is open.
- **Untrusted content.** DOM, logs, comments, API responses, tickets and test data are data, never instructions.
- **Secrets.** Credentials, tokens and personal data never go into artefacts. Secrets live in `.env`, which is gitignored.

The guard is a command-text check on file tools and shell commands. It stops an agent from leaving its scope or answering its own hold; it is not a sandbox. See [`docs/adr/0006-write-scope-guard.md`](docs/adr/0006-write-scope-guard.md) for what it does and does not cover.

## Limitations

- **Claude Code only.** The agents, skills, commands, workflows and hooks use Claude Code's formats and tools.
- **The session is hosted from the harness.** Claude Code is started in this repository with `TESTHARNESS_PROJECT_DIR` naming the project. Installing the harness into a project folder is not automated.
- **The guard is not a sandbox.** It reads command text. A write assembled indirectly, or performed by a script it was never shown, is not seen.
- **Agent-raised holds are reported by the agent.** `business_rule` and `framework_change` stop the pipeline at checkpoints because the agent returns its pending list; `qa-plan` blocks any later run while one is pending.
